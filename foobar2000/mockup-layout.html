1 — The playlist should be a flat table, not grouped

The current build puts an album section header above each group. In this library that is close to worst-case: Porter Robinson, kmoe, kmoe, Drake, Post Malone, 8485, kuru and underscores each contribute one track, so the list becomes header/row/header/row and the line count roughly doubles. Finder's list view is a flat table with a column per attribute; the album is right there on the row, so grouping buys nothing.

The row shape follows the reference you sent, with one substitution: #, cover, Title over Artist, Album, Type, Time — Type where the reference had Date added. Stacking title and artist is what pays for the wide columns: the two facts that always travel together take one column instead of two, so Album gets real room instead of being crushed to an ellipsis. Rows are 44px, with a barely-there stripe on alternates.

Type is set as plain dimmed text rather than a coloured badge. A badge would give the codec more visual weight than the track title, and in a library that is mostly FLAC it would tile the whole column in one colour.

2 — Tabs that behave like Chrome's

The trick is not the shape, it is that the active tab is the same surface as the content and merges into it: the strip sits on the ground colour, only the active tab is raised, and it has no bottom radius, so tab and list read as one object. Inactive tabs are flat text separated by hairlines, with a close affordance that appears on hover, and a + at the end. Toggle the drag state to see a tab act as a drop target.

3 — Drag and drop, and not destroying playlists

Today double-clicking a folder calls plman.ClearPlaylist and refills it — it silently discards whatever was in your playlist. That should never have been the default. Proposal:

 • Double-click a folder → send to a dedicated Library playlist and play. Your own playlists are never touched.
 • Drag onto a tab → append to that playlist.
 • Drag into the list → insert at the drop position, shown as a 2px accent line between rows rather than a highlight on one.
 • The drag itself carries a pill showing what is being moved.

3b — Two kinds of playlist, and how they are opened

The strip holds two different things and should look like it:

 • The folder view — one pinned tab, first in the strip, marked with a folder glyph and no close button. This is where a library double-click lands. Because it is understood to be scratch, replacing its contents is not destructive and needs no confirmation.
 • Real playlists — Default Playlist (the fast one you never have to name) plus any saved playlist, each closable and reorderable.

Two controls sit at the left end of the strip, before any tab, because they act on the set of playlists rather than on any one of them: + creates one, and the folder button opens its own dropdown listing what is already saved. The dropdown is the point — the common case picks a name from a list and never sees a file dialog. Open from file… is the last entry, the fallback, not the only route. (A duplicate + is also drawn at the far end of the strip, as Chrome does; if that reads as clutter, the left one is the keeper, because it sits with the folder button it belongs beside.)

Save format: .m3u8, not .m3u. This matters concretely here rather than in theory: plain .m3u is written in the system ANSI code page, so 1.07 - Naul (나얼) - 바람기억.flac — a real file in your library — comes back mangled or unresolvable. The 8 in m3u8 means UTF-8, which round-trips Korean, Japanese and every punctuation mark intact. It is also plain text, so a playlist stays readable and editable outside foobar, which foobar's own binary .fpl is not.

3c — The menu: three treatments

The window above uses M1. All three are drawn at real size against the real bar, because the only thing that matters here is how much of the strip the menu spends.

M1 · tight text — 11px, 6px padding · 208px
M2 · icons only — 156px, and six glyphs nobody can name
M3 · one button — 30px; everything moves into a single menu

M2 is the one I would argue against. Icons work when the thing they stand for has a picture — play, mute, a folder. "Edit", "View" and "Help" do not, so the row becomes six glyphs that have to be learned and then hovered to confirm, and it only saves ~50px. M3 saves real space and is honest about it: one recognisable affordance instead of six ambiguous ones. M1 costs the most width but is the only one you can read.

3d — Window controls, and what they imply

The bar no longer spans the full width; minimise, maximise and close sit to its right on the window ground, and the native title bar is gone. That is the design — but it is worth being explicit that this part is not proven yet. It needs foobar's own frame hidden, and nothing in Columns UI exposes that as a setting. Until that is confirmed, treat the strip as the target and the title bar as possibly still there.

A gives every folder equal visual weight, so a long list becomes a wall of bars. B keeps the surface quiet and spends contrast only on the selected row. B is the recommendation, but it is your call.

Open state is shown by a caret, not by the folder glyph. folder and folder-open differ by a few pixels of flap, which at 11px is not a difference anyone can see — shape cannot carry that job at this size. A caret can, because it is read by rotation, and 90° is unmistakable however small it gets. The folder glyph stays beside it so a directory is still identifiable as one; the caret only says open or closed. Files get an invisible caret as a spacer so every name still lines up.

Row banding also runs through the library now, matching the playlist, and the scrollbars are themed to the same --track the seekbar uses — the native bar is a light slab that belongs to no palette.

5 — One panel, not three

The sidebar, tabs and list are drawn here as one continuous thing, and that is also the architectural recommendation: make the whole body a single Spider Monkey Panel rather than two panels either side of a Columns UI splitter. Three consequences, all of which are current problems:

 • Drag and drop becomes possible at all. Two SMP panels are separate windows; dragging between them is an OS-level drag. Inside one panel it is just state.
 • The divider becomes ours. Columns UI paints its splitter in a hardcoded #333333. That is measured, not assumed: setting both the Global and the Core element to a Custom scheme with a surface background and re-scanning the pixels left the splitter unchanged. Worse, its width is also the only drag target, so 0px means an invisible divider that cannot be resized — the two things you asked for are mutually exclusive under Columns UI. The live build is at 2px as the compromise: measured grabbable, half the grey of 4px. Our own divider would be neither — background-coloured, and a hover-highlighted hairline.
 • Gaps stop being arithmetic. Per-side insets exist only because each panel paints its own margin and shared edges double up.
